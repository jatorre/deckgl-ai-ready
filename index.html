Q2 · How well do frontier models write deck.gl?

How we tested it

Five maps to build. One prompt each. No tools, no docs.

  1. World airports as styled points with tooltip and legend
  2. Choropleth of 4,627 Vancouver blocks, skewed data, classed legend
  3. 3D hexagons of 140k UK accidents with a radius slider
  4. Animated taxi trips with play/pause
  5. Open brief: "the most impressive deck.gl visualization you can build"

How we scored the outputs

  • Each file rendered in a headless browser; errors, failed requests and library versions captured
  • Screenshots at 3, 8 and 14 seconds
  • A model judge scored each map on a fixed rubric: renders, meets the brief, cartography, interactivity, current API
  • Then we looked at every one

Seven models: Opus 4.8, Fable 5.1, GPT-5.6 Sol, GPT-6 Astra, Gemini 3.1 Pro, Gemini 3.8 Flash, GLM 5.3. Real public data, CDN scripts only, no API keys.

The judge is Claude Fable 5.1 reading the code, the render report and the screenshots, so it could favor Claude; version and API facts are checked mechanically from the files, not by the judge.

Q2 · How well do frontier models write deck.gl?

The open brief is where they differ

Same data, no requirements beyond "impress a demanding visualization designer". This is where ambition and depth separate: how many layers, whether there is a camera, lighting, a UI, and whether it all actually runs.
Q2 · How well do frontier models write deck.gl?

Working maps, written like it's 2024

  • The code is a generation behind. Most files load a deck.gl 8.9 bundle or use v8 patterns; only GPT-5.6 Sol used the current overlay integration; none used 9.2 or later.
  • They copy the showcase examples. The hexagon and trips tasks pulled every model toward the official example's stack, palette and defaults, v8 included.
  • Same cartographic choices, same blind spots. Every choropleth is YlOrRd quantiles; skewed data goes unhandled; legends vanish when not demanded. Good, never excellent.
  • The open-weight model knows the words, not the rules. GLM 5.3 mutated layer props instead of replacing layers and shadowed the library global.

Conclusion. Our examples are the training data, and they are years old. The open brief shows what models can build now. Update the examples with AI, and the next generation of models learns deck.gl from those.

Speed is not quality: Gemini 3.8 Flash produced the most code per second and the nicest panels and scored lowest on API currency. The gap is not capability; it is freshness and unwritten rules, and the cheapest lever we own is the examples. The hexagon and trips examples are what every model reproduced, stack and palette included. If those examples were current, ambitious and correct, the models would be too. Rules like "layers are immutable, replace them" are what a schema or a skill would carry. That is questions three and four.
Q3 · How can agents drive deck.gl interactively?

Many applications will use deck.gl with agents to drive dynamic maps

Not "write me an app" but "show me", "filter that", "color it by income", while the map is running. The most logical interface for that is one deck.gl has had since 2018: the agent writes declarative JSON.

We are lucky to have it: declarative, portable, no eval, and models already know its syntax. What follows is how far it gets us today, and what is missing.

Alternatives exist: generate code, or expose verbs as tools. Both are heavier. A document the agent writes and the app renders is the natural fit, and MCP Apps now lets that document render inside the chat itself.

Q3 · How can agents drive deck.gl interactively?

How CARTO does it, two ways

Verbs on a live map

The in-app assistant has about 27 tools: add source, add layer, set style, filter. It edits the running map's state one call at a time.

Stateful and precise. But every rule lives in prose ("add the layer right after the source") and nothing checks it.

A document the agent writes

The agent emits a complete @deck.gl/json spec. An MCP App renders it inside the conversation; the same spec can be re-rendered in any app.

Stateless and portable. But the agent never sees the result; only errors come back.

Both work in production. Both hit the same wall.

The document path is stock @deck.gl/json 9.3 with a whitelist of seven CARTO tile layers, thirteen source builders wrapped to inject the token, and three color helpers. The whitelist is the schema, because there is no schema.
Q3 · How can agents drive deck.gl interactively?

The problem: nothing fails loudly

36 KB
of instructions an agent must read to write a valid spec

Half of it lists ways to get an empty map with no error: wrong layer, wrong layer-source pairing, missing aggregation, deep expression.

0
errors when a layer type is unknown

Upstream: log.warn, returns null. The docs: "Error detection is currently limited and error messages may not be very helpful."

1.9 MB
JSON Schema we validate Vega-Lite charts against, in the same service

For deck.gl specs we count layers before and after conversion. Charts get a type system. Maps get prose.

  • An agent recovers from any error it can see. It cannot recover from an empty map, so we send errors only, passively, with the legal alternatives spelled out. Silence equals success.
  • The loop is write-only. No viewport, counts or clicks come back. The agent cannot look at its own map.
Actively messaging the model about a failure over an optimistic tool result made it oscillate and retry identical arguments. Everything on this slide is a workaround for one upstream behaviour.
Q3 · How can agents drive deck.gl interactively?

Can frontier models write the spec? Mostly. And the failures are silent.

Opus 4.8Fable 5.1GPT-5.6 SolGPT-6 AstraGemini 3.1 ProGemini 3.8 FlashGLM 5.3
invented helpervalidCARTO helpervalidvalidvalidinvented helper

Task: a choropleth of countries by population, as @deck.gl/json. Every model got the @@type syntax and the view right. The failure is always in the same place: the data-driven color.

Four wrote a valid expression. One used CARTO's helper vocabulary, which only exists in our registry. Two invented a helper that does not exist. Older models reached for Mapbox style expressions.

"getFillColor": {
  "@@function": "interpolateColor",   ← does not exist
  "value": "@@=properties.population", ...
}

What the user sees: a map with no fill, and no error. The agent thinks it succeeded.

This is the crux. Models write the declarative format well; what they cannot know is the vocabulary that lives outside the format, and the runtime does not tell them when they guess wrong. A schema would catch every one of these before rendering.
Q3 · Proposal

Make @deck.gl/json v2 the agent interface

  1. JSON Schema from Zod, including the compatibility rules. Validation, structured outputs, editors.
  2. Loud failure. A conversion report (ok · partial · error, dropped items with reasons) instead of warn-and-drop.
  3. State read-back. Viewport, layers with counts, picked object, optional screenshot. Finish the 2018 back-channel. Ship a reference MCP App.
  4. Patch semantics for multi-turn editing.
  5. A data-source concept for SQL, tiles, Arrow and COG.
  6. Registry profiles. Core plus vendor registries, published with their schemas.

Two provocations

  • Accept Mapbox-style expression arrays as an accessor syntax. Models already speak it.
  • Standardize one color-scale vocabulary in core. Today there are three, plus what models invent.

Step 1 of the v2 tracker, GeoJSON schemas, has been an open PR since 17 April. This proposal is written up as a draft RFC, visgl/deck.gl #10679, with CARTO's evidence and an offer to help drive it. Let's finish what Ib started in 2018.

deck.gl does not need to speak natural language. It needs to be checkable, so a model's fluency in JSON is enough. Name the tension: the 2018 "One API" principle versus a smaller, stricter agent profile. We broke One API on purpose with a closed registry; make that a supported pattern.

Q5 · How do we handle AI contributions?

deck.gl briefs the agents, but has no policy for their contributions

  • deck.gl has an AGENTS.md telling agents how to contribute. Its contributing guide, PR template and every TSC document tell humans nothing about contributing with AI.
  • Elsewhere: bans (Zig, Gentoo, QEMU, Bevy, GIMP) · disclosure (curl, Linux, Apache, LLVM, Kubernetes, NumPy) · conditional (CPython, PyTorch).
  • OpenJS Foundation, after the 19,000-line Node.js PR built with a coding agent: the DCO covers AI-assisted code.
  • Already in our ecosystem: a deck integration planned "with the help of gpt-5.4"; three AI-forward RFCs in one day; this talk.

Suggestions

  • Disclosure: an Assisted-by: trailer; the contributor understands and has tested the code
  • No AI on good-first-issues, LLVM's rule
  • A PR template checkbox
  • Point AGENTS.md and the developer process at the same policy: those docs are now the agent's instructions too
The maintainers' fear is slop and review burden, and it is legitimate. Disclosure plus "you understand and tested it" plus protecting good-first-issues is where most mature projects landed. We only need to write it down.

Backup · Q2 detail

GLM 5.3, the open-weight model

  • Its endpoint makes reasoning mandatory. Default: 24,000 tokens of thinking, no HTML, about 400 s per task. Only an explicit 8,000-token reasoning cap produced files, in 10 to 33 s.
  • One earlier map pinned deck.gl@8.10.1, which does not exist.
  • Choropleth: const deck = new deck.Deck(...) shadows the library global; loads Mapbox GL JS, which demands a token. Blank page.
  • Hexagons: hand-rolled TileLayer reading props.bbox instead of props.tile.bbox; hexagons on black.
  • Trips: mutates layer.props.currentTime and calls internal setState instead of recreating the layer; the animation dies on frame one.
